### 수집 경로

- 이 검증의 요청: `DISFundFTimeAnnSO.selectAnn`, `vStrtDt=20260813`, `vEndDt=20260815`, `uGb=1`, `gbOption=S`, `uRptAllYN=1`, 나머지 빈 값
- 결정: 수집 층은 이 단일 엔드포인트 사용. 화면 크롤링 불필요
- 근거: 응답이 페이징 없이 전건을 한 번에 반환. 3일 조회에 `dbio_total_count_` 1,499와 `<list>` 행 1,499 일치
- 주의(실측): `uRptAllYN`을 0으로 두면 오류 없이 0건. 수집 모듈은 0건을 정상으로 넘기지 말고 경보 대상으로 둠
- 주의(실측): Python `urllib`로 받으면 응답이 중간에 잘림(1,499행 중 43행만 도착). `curl`은 정상. 스크립트는 `curl`로 전송하고 응답이 `</root>`로 끝나는지 확인한 뒤에만 결과를 씀. 잘린 XML은 파서가 행을 오류 없이 적게 세므로 종료 태그 확인 필수

### 15행의 정체

티켓 사례(미래에셋밸런스롱숏, 2026-08-14, DART 접수번호 20260814000852)를 조회하면 정확히 15행.

| | 행 수 | `uFundNm` 표기 | `tmpV1` |
|---|---|---|---|
| 모펀드 | 1 | `미래에셋밸런스롱숏증권자투자신탁 1(채권혼합)` | 자기 `standardCd`와 같음 |
| 클래스 | 14 | `└▶…종류A`, `종류A-e`, `종류C1`~`C4`, `종류C-e`, `C-I`, `F`, `S`, `C-P`, `C-Pe`, `C-P2`, `C-P2e` | 모펀드의 `standardCd` |

판정: 「15 = 화면 기본 조회 건수(페이지 크기)」라는 09-14 외부 확인의 반론은 채택하지 않음. 근거 셋:

1. API가 페이징 없이 3일치 1,499행을 한 번에 반환. 15는 어떤 페이지 크기도 아님
2. 같은 날 같은 조회에서 묶음 크기가 1부터 234까지 흩어짐(「자연키 검증」). 15가 상수였다면 불가능
3. 15행이 종류A·C1~C4·F·S처럼 실제 클래스 표기를 하나씩 달고 있음. 09-14 메모의 「종류형 클래스가 15개이기 때문」 해석이 맞음

- 15는 이 펀드의 수일 뿐 상수가 아님. 9월 교차 표본에서는 최대 묶음이 18행. 설계 문서에서 「15행」을 규칙처럼 쓰지 않음
- 파싱 신호(실측): 클래스 행은 `uFundNm`이 `└▶`로 시작. 1,499행 중 클래스 1,087행 / 모·단독 412행으로 완전히 갈림. 유사도나 문자열 추측 불필요

### 자연키 검증

당시 논리 스키마가 금투협 `source_doc_key`로 제안한 `(companyCd, standardDt, announceTtl, tmpV1)` 해시를 표본에 적용.

| 키 | 묶음 수 | 묶음 크기 최대 | 평균 |
|---|---|---|---|
| `(companyCd, standardDt, announceTtl)` — tmpV1 제외 | 91 | 234 | 16.5 |
| `(companyCd, standardDt, announceTtl, tmpV1)` — 제안 키 | 882 | 15 | 1.7 |

- 결정: 4항목 자연키 확정. 현행 → [데이터 테이블·ERD 설계](../../data-model.md) 「문서와 소스별 키」
- 근거: `tmpV1`을 빼면 삼성자산운용 2026-08-13 「투자설명서 변경」 한 묶음에 서로 다른 펀드 72종 234행이 한 묶음으로 합쳐짐. 운용사가 같은 날 같은 제목으로 여러 펀드를 한꺼번에 공시하므로 제목과 날짜만으로 공고를 가를 수 없음

### 수시공시만 1:N

`uRptGb`가 정기/수시를 가름. 표본에서 `uRptGb`와 `tsCd` 접두가 100% 일치(O↔`2OF` 853행, R↔`2RF` 646행).

| 구분 | 행 수 | 자연키 묶음 | 묶음 크기 최대 | 평균 | 뜻 |
|---|---|---|---|---|---|
| 수시 `2OF` (투자설명서 변경, 집합투자규약 변경) | 853 | 282 | 15 | 3.02 | 문서 1건이 클래스 여러 건을 덮음 |
| 정기 `2RF` (자산운용보고서, 자산보관·관리보고서, 회계감사보고서) | 646 | 600 | 9 | 1.08 | 사실상 행 1개 = 문서 1건 |

- 결정: 문서_상품 브릿지는 유지하되 1:N이 실제로 발생하는 것은 수시공시(`2OF`)뿐임을 명시. 정기공시는 클래스·펀드마다 별도 보고서
- 함의: 「같은 PDF를 15번 내려받는다」는 낭비는 수시공시에만 해당. 정기공시에 중복 제거를 걸면 서로 다른 보고서를 하나로 지움 → 중복 제거 규칙은 `uRptGb = 'O'` 조건 필수

### tmpV1 의미와 코드 체계 혼재

답: 공시 유형에 따라 의미가 바뀜. 한 칸에 두 의미.

| 공시 구분 | 클래스 행의 `tmpV1` | 확인 |
|---|---|---|
| 수시 `2OF` | 모펀드 코드 (자기 `standardCd`와 다름) | 투자설명서 변경 439행, 집합투자규약 변경 131행 전부 |
| 정기 `2RF` | 자기 코드 (`standardCd`와 같음) | 자산운용보고서(공모) 382행, MMF 44행, 자산보관 34행 전부 |

화면 JS(`/js/meta/disMeta.js`) 주석도 수시 기준으로 같은 내용:

```js
var prCd = oGrdMain.getCellData(rowIdx,'tmpV1');      //모펀드코드
var chCd = oGrdMain.getCellData(rowIdx,'standardCd'); //자펀드코드
```

코드 체계가 한 칸에 섞임:

| 칸 | `K55…`(금투협 펀드코드) | `KR5…`(협회표준코드) | `KRM…` | `ZZZ…` |
|---|---|---|---|---|
| `standardCd` | 887 | 603 | 9 | 0 |
| `tmpV1` | 826 | 631 | 9 | 33 |

- 결정: `standardCd`·`tmpV1`을 상품 `standard_code` 한 칸에 그대로 넣지 않음. 적재 시 접두 3자로 분기해 `K55…`는 `kofia_fund_code`로, `KR5…`·`KRM…`은 `standard_code`로
- 근거: 한 묶음 안에서도 두 체계가 섞이는 사례 24건(키움투자자산운용 2026-08-13 집합투자규약 변경 등). 소스나 공시 유형으로 미리 가를 수 없고 값 자체를 봐야 함
- `ZZZZZZ…` 해소: 모펀드 행 표시자. 화면 JS가 `result == "O" && (prCd.indexOf('ZZZZZZ') != -1 || prCd == chCd)`를 「수시 - 모펀드만 구분표시」 조건으로 사용. 수시공시 모펀드 행은 `tmpV1`이 자기 `standardCd`와 같거나 `ZZZZZZ…` 표시값을 가짐. 자연키에 그대로 써도 문제없음

### 첨부 해시 비교

- 수시공시 상세는 `DISFtimeDetSO.select`로 조회. 응답 `file` 노드의 각 항목이 `fileNm`(서버 저장명)·`serverPath`·`originalFileNm` 제공
- 다운로드는 별도 호스트 `disdown.kofia.or.kr/COMFSFileDownload.jsp`. 호출 형식은 [데이터 소스 수집 명세](../../data-sources.md) 「첨부 목록 — `DISFtimeDetSO.select`」
- 묶음 4개(운용사 4곳, 14~15행)에 대해 행마다 상세를 조회하고 첨부를 전부 내려받아 sha256 비교

| 운용사 | 기준일 | 공시 | 행 수 | 첨부 | 행별 첨부 집합 |
|---|---|---|---|---|---|
| 미래에셋자산운용 | 2026-08-14 | 투자설명서 변경 | 15 | 3건 | 1종 |
| 한국투자신탁운용 | 2026-08-13 | 투자설명서 변경 | 15 | 3건 | 1종 |
| 키움투자자산운용 | 2026-08-13 | 집합투자규약 등 변경 | 14 | 2건 | 1종 |
| 삼성자산운용 | 2026-08-13 | 투자설명서 변경 | 14 | 3건 | 1종 |

- 판정: 한 묶음의 모든 행이 완전히 같은 파일 집합을 가리킴
- 미래에셋 15행의 투자설명서는 15행 전부 sha256 `06aa1962b7d5e6d1…`, 1,022,426바이트로 동일
- 결정: 문서 단위 「수집한 원천 문서 1건」과 클래스 행 중복 제거 확정
- 근거: 행 단위로 수집하면 같은 PDF를 15번 내려받고 15번 추출하게 된다는 티켓 메모의 우려가 실측으로 확인됨

### 파일명 중복 제거 판단

- 결정: 금투협 중복 제거는 다운로드 전에 `fileNm`(서버 저장명) 비교로 끝냄. sha256은 검증용
- 근거: 4개 묶음 전부에서 `fileNm` 고유 수 = sha256 고유 수(각 1종). 금투협이 서버 측 고유 파일명을 주므로 같은 파일인지 알려고 15번 내려받을 필요 없음. 예: `1e8761fba739f6722daf996c19fd6720d26-3081-20260814100636.pdf`
- 함의: CAS(`blobs/{sha256}`) 채택을 2단계 데이터 파이프라인 Flow 설계로 미룬 판단은 유지 가능. 금투협 중복 제거라는 당면 근거가 `fileNm`만으로 해소됨. CAS는 소스 간 중복이라는 다른 근거가 생길 때 다시 판단
- 이후 현행 규칙: 같은 공고 안의 `server_path + fileNm`. [원본 보관과 수집·파싱 실패 처리 규칙](../../storage-and-failure-rules.md) 「금투협 클래스 행 중복 제거」

### 첨부 2~3건

- 한 공고의 첨부는 투자설명서·간이투자설명서·변경대비표(또는 규약) 조합
- 원본파일(raw_object)을 문서 하위 파일 단위 표로 둔 구조가 맞음
- 주의: 간이투자설명서가 금투협에도 첨부로 옴. DART 쪽 간이투자설명서와 합치면 두 소스에서 같은 내용을 받을 수 있음. 소스 간 중복 제거 규칙은 없음 → 이후 DART 쪽은 투자설명서 PDF 안의 요약 정보 절로 확인([DART 본문 PDF 부·절 분할 실현성 검증](dart-section-split.md) 「함의」)
- 미확인: `txVsn`을 0으로 주면 SQL 예외. 목록이 주는 값을 그대로 넘기면 되지만, 값이 비어 오는 행이 있는지는 확인하지 않음

### 포털 집계

`getStandardCodeInfo` 전건을 1,000건씩 184페이지로 받아 `fndNm`을 NFKC 정규화·공백 제거 후 「상장지수」 포함 여부를 셈.

| 항목 | 값 |

### 이름 공간 차이

- 티켓 지시: 「`fndNm`에 「상장지수」가 포함된 집합을 뽑아 정규화 문자열로 대조」
- 실행 결과 두 소스의 이름 공간이 다름

| 소스 | 필드 | 값의 성격 | 예 |
|---|---|---|---|
| 공공데이터포털 | `fndNm` | 정식 펀드명 | `하나1Q200액티브증권상장지수투자신탁[주식]` |
| KRX | `ISU_NM` | 상장 약명 | `1Q 200액티브` |

| 방식 | 결과 |
|---|---|
| 완전일치 (티켓이 지시한 방법) | 0 / 1,167 = 0.0% |
| 포함매칭 (NFKC + 공백 제거) | 931 = 79.8% (단독후보 842) |
| 포함매칭 + 기호 전부 제거·대문자화 | 938 = 80.4% (단독후보 847) |

- 티켓 방법을 그대로 실행했다면 누락률 100%로 규칙이 채택되지 않았을 것. 규칙의 잘못이 아니라 이름 공간 차이 때문
- 정규화를 아무리 강화해도 80.4%가 최대치
- 남은 229건은 `ACE 국고채3년`·`ACE 단기통안채`·`ACE MSCI멕시코(합성)`·`ACE 골드선물 레버리지(합성 H)` 형태. 브랜드 개명(ACE는 구 KINDEX)과 `(합성)`·`(합성 H)` 표기 차이가 섞임. 문자열로 더 좁힐 수 없음
- ETF 종목코드(`ISU_CD`)와 펀드 단축코드(`srtnCd`)를 잇는 코드 소스가 없다는 문제가 그대로 드러남. 이름이 유일한 축이며 그 축이 80.4%만 붙음

### 스크립트 동작 정정 (09-20)

- 초판 기록: 「KRX 이름 후보 필드마다 완전일치 수를 세어 최선을 고르고, 50% 미만이면 중단」
- 실제: 그런 방어는 스크립트에 없음. 완전일치 0.0% 확인 후 포함매칭으로 다시 짜면서 분기를 지웠고 기록 문단만 남아 있었음
- 현재 `verify_etf_rule.py`는 `ISU_NM`을 고정으로 쓰고, 붙지 않은 건을 오답이 아니라 「매칭 실패(판정 불가)」로 따로 세어 거짓 누락률을 막음. 목적은 같고 수단이 다름

### 누락·오탐 측정

누락: KRX ETF 1,167건을 전체 펀드 183,649건에 포함매칭으로 붙이고, 붙은 펀드명에 「상장지수」가 있는지 확인.

| | 건수 |
|---|---|
| 매칭됨 | 938 (80.4%) |
| ├ 펀드명에 「상장지수」 있음 | 938 |
| └ 펀드명에 「상장지수」 없음 (실제 누락) | 0 |
| 매칭 실패 (판정 불가) | 229 |

- 누락률 0/938 = 0.00%. 붙는 범위 안에서는 규칙이 ETF를 한 건도 놓치지 않음. 1% 기준 통과

오탐:

| | 건수 |
|---|---|
| 규칙 적중 | 1,435 |
| ├ 어떤 KRX ETF와 붙음 | 1,000 |
| └ 아무 KRX에도 안 붙음 | 435 |

- 오탐 상한 435/1,435 = 30.3%
- 435건 안에 매칭 실패 229건이 섞여 있어 전부 빼면 하한 206/1,435 = 14.4%
- 어느 쪽이든 1% 기준을 크게 넘음
- 안 붙은 435건 중 2015년 이전 설정이 110건(25%). 상장폐지 ETF가 마스터에 남은 것으로 보임. 나머지도 비상장 「상장지수」 명칭 펀드일 수 있음

### 판정

- 티켓 기준: 「누락과 오탐이 각각 1% 미만이면 규칙 유지, 오탐이 유의미하면 문자열 규칙을 보조 신호로 낮추고 KRX 대조를 1차 판정으로 승격」
- 오탐이 유의미하므로 승격

결정 (09-19): ETF 판정을 2단으로 변경.

1. 1차: KRX `ISU_CD` 대조로 확정. 붙으면 `KRX_CONFIRMED`
2. 2차: 「상장지수」 문자열 규칙은 후보 선별용으로만 사용
3. 1차가 실패한 잔여는 보류하고 목록으로 남김(매칭 실패 229건)

- 원 기록의 「재현율이 100%라 후보를 놓치지 않는다」는 대체됨 → 0/938은 붙는 938건 범위 안의 값이며 「재현율 100%」로 읽지 않음(09-22, 「정정 이력」)
- 근거: 누락은 0/938이나 정밀도가 낮음(오탐 14~30%). 상품군 분류가 틀리면 CDI 측정 대상 집합이 틀어져 비교 모집단이 왜곡됨. 과매칭이 미매칭보다 비싸다는 매칭 원칙과 같은 판단
- 함의: 상품 `is_etf`를 `product_name` 파생 칼럼으로만 두면 30%까지 과잉 포함. KRX 대조 결과를 담을 칸(`isu_cd`와 판정 신뢰도)이 필요 → 이후 `etf_confidence` 4상태로 반영([상품·법인 매칭 규칙](../../matching-rules.md) 「ETF 판정」)
