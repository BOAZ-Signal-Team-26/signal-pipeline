## 매칭 경로

대상이 상품명인지 법인명인지에 따라 규칙이 다름. 두 규칙을 섞지 않음.

| 연결 | 대상 | 수단 | 적용 규칙 | 기준 |
|---|---|---|---|---|
| DART 표지 펀드코드 ↔ 상품 `short_code` | 상품 | 코드 | 「코드 매칭」 | 후보 1개일 때만 연결 |
| 금투협 판매사별 펀드 ↔ 판매관계 | 판매사 | 코드(`saleCompCd` + `tmpV17` 표준코드) | 문자열 매칭 불필요 | — |
| KRX `ISU_CD` ↔ 상품 `isu_cd` | ETF | 이름(포함매칭) | 「ETF 판정」 | 붙는 범위 최대 80.4% |
| 제재공시 `finInstName` ↔ 법인 | 판매사 | 법인명 문자열 | 「법인명 정규화」 5단계 | 0.95 + 자동 확정 금지(「제재공시 법인 매칭」) |
| 코드 조인 잔여 상품 | 상품 | 상품명 문자열 | 「상품명 정규화」 4단계 + 「하드 룰」 | 0.85 자동 / 0.60~0.85 수동 |
| 분쟁조정결정례 | — | 없음 | 매칭 시도 안 함 | — |

- 법인명에 상품명 규칙을 쓰지 않는 이유 둘
  - 법인명에는 호수·클래스 표기가 없어 상품명 4단계가 할 일이 없음
  - 법인명에는 상품명에 없는 상호 변경이 있음. 운용사 536건 중 97건(18%)이 구 상호를 갖고, 그중 44건은 업종 접미사까지 바뀜(「누림투자자문」 → 「누림자산운용」)
- 펀드코드가 10건 실측에서 전부 있었으므로 Phase 1(펀드·ETF, 9차 미팅) 문자열 매칭의 주 대상은 제재공시 금융회사명과 코드 조인 잔여 상품명. ELS 상품명은 Phase 1 범위 밖(9차 미팅), Phase 2 검토
- 조인 판정 현황 전체: [조인 키 확인 기록](records/phase1-erd/join-key-checks.md) 「조인 키 확인 현황」

## 코드 매칭

| 항목 | 내용 |
|---|---|
| 1차 키 | DART 표지 펀드코드 = 공공데이터포털 `srtnCd` = 상품 `short_code` |
| 형식 | `[A-Z0-9]{5}`. 165,118종 전부. 「영문 1 + 숫자 4」가 아님 |
| 출처 | 공공데이터포털 `srtnCd`를 그대로 사용. 표준코드 substring 파싱으로 만들지 않음 |
| 성질 | `srtnCd == asoStdCd[6:11]`. 독립 코드가 아니라 표준코드 12자리 안의 한 토막 |
| 대조 실측 | DART 표지 10건 중 7건이 `srtnCd`에 존재. 나머지 3건(EY758·EZ258·EZ029)은 포털 미등록 → PENDING_MASTER(정상 대기) |

유일성:

| 범위 | 겹침 |
|---|---|
| 전체 고유 `srtnCd` 165,118종 | 4,899종(3.0%)이 2건 이상 공유. 전부 `asoStdCd`도 다른 별개 펀드 |
| 2015년 이후 설정 펀드끼리 | 5종(10행) |
| 「상장지수」 1,435건 안 | 0종 |
| `(asoStdCd 앞 6자리, srtnCd)` 쌍 | 183,648종 중 1종 |

규칙 (09-22):

- `short_code`는 조인에 쓰되 UNIQUE가 아님
- 단축코드가 같다는 이유로 첫 행을 선택하지 않음. 전체 코드·운용사·모자·호수·클래스 식별을 대조
- 해소되지 않는 다중 후보는 AMBIGUOUS
- `fund_key` 묶음은 클래스 표기만 제거하고 호수·모자 구분은 제거하지 않음
- 겹침이 실제로 문제가 되면 `(asoStdCd 앞 6자리, srtnCd)` 쌍으로 올림. `asoStdCd`는 상품 표의 `kofia_fund_code`(K55 체계) 또는 `standard_code`(KR5/KRM 체계)에 있어 스키마 변경 불필요
- 코드성 식별자(사업자등록번호·`corp_code`·`kofia_mgmt_code`·`saleCompCd`)가 있으면 문자열 매칭 전에 코드로 붙임. 단 DART 법인과 금투협 운용사 코드는 1:1이 아님(대응표에 없는 값 7종, 처리는 아래 「대응표에 없는 운용사 코드」)

## 운용사 연결 순서 (10월 4일 PM 승인)

펀드(1순위)와 ETF(2순위)에 같은 순서를 씀. 상품을 운용사(`distributor`)에 붙일 때 위에서부터 시도하고 처음 붙는 단계에서 멈춤.

| 순서 | 키 | 근거 | 비고 |
|---|---|---|---|
| 1 | 금투협 공시 목록의 운용사 코드 `companyCd`(`A01021` 형식) → `distributor.kofia_disclosure_company_code` | 공시 행마다 현재 운용사 이름과 함께 나옴. 합병·상호 변경 반영 | 공시 행을 적재할 때 채움. 공시가 없는 상품은 수집할 문서가 없어 점수 대상이 아님 |
| 2 | 표준코드 4~6번째 자리 → `distributor.kofia_mgmt_code`(대응표) | K55 체계는 펀드명과 대응표 운용사명 일치 약 91% | 펀드 설정 당시 운용사라 합병 뒤에는 틀릴 수 있음. KR5 체계는 일치 약 57%라 2단계 결과만으로 연결한 KR5 상품은 확인 대상 |
| 3 | 연결 실패 | | `match_failure`에 `NO_CANDIDATE` |

- 1순위 펀드 작업에서 공시를 수집할 때 1단계 칼럼을 채워 두면, ETF를 붙일 때 추가 수집이 필요 없음
- 근거와 조회 결과: [운용사 코드 대조 기록](records/phase1-erd/manager-code-check.md) 「KR5 체계와 운용사 연결 순서」

## 코드 체계 분기 (ERD v2.2, 결정 대기 E)

- 공공데이터포털 `asoStdCd`에 K55 체계와 KR5 체계가 섞여 있음. ETF 대조 표본 1,373건 중 K55 1,195건, KR5 178건
- v2.1은 `standard_code` 한 칸(KR5/KRM 전용)만 있어 `kofia_fund_code`를 채울 소스가 없었고, 금투협 K55 887행의 조인이 실패함
- 기본값(체계별 두 칼럼): 접두 3자로 분기. `K55…`는 `kofia_fund_code`, `KR5…`·`KRM…`은 `standard_code`. 어느 쪽도 아닌 접두는 어느 칼럼에도 넣지 않고 원본에 보존(처리 방식은 「미결」)
- 금투협 수시공시 코드(`tmpV1`, `standardCd`)도 같은 규칙으로 분기([조인 키 확인 기록](records/phase1-erd/join-key-checks.md) J7)
- 같은 펀드를 포털(K55 값)과 금투협(K55 값)에서 조인할 때는 `kofia_fund_code`끼리, KR5/KRM 값끼리는 `standard_code`끼리 비교. 체계가 다른 값끼리는 비교하지 않음
- 반대 결정(한 칸 병합 등)이면 이 절과 product 칼럼 두 개만 바뀜

## ETF 판정

| etf_confidence | 판정 근거 | is_etf / product_category | 비교 모집단 |
|---|---|---|---|
| KRX_CONFIRMED | KRX `ISU_CD` 대조로 확정 | true / ETF | 나머지 자격 충족 시 포함 |
| NOT_ETF | 비ETF 확인 근거가 있을 때만 | false / 확인된 펀드 또는 ELS | 펀드는 자격 충족 시 포함, ELS는 CDI 제외 |
| NAME_ONLY | 이름에 「상장지수」 포함, KRX 미확인 | NULL / NULL | 제외 |
| PENDING | KRX 대조 실패 잔여 | NULL / NULL | 제외 |

- 1차: KRX 목록 대조. 2차: 「상장지수」 문자열은 후보 선별용
- 이름에 「상장지수」가 없다는 이유만으로, 또는 KRX 미매칭만으로 NOT_ETF를 확정하지 않음
- 판정 결과와 판정 단계는 상품 표 `etf_confidence`에 남김. 표 규칙은 [데이터 테이블·ERD 설계](data-model.md) 「상품과 법인」

측정값 (09-19, 공공데이터포털 183,649건 × KRX 1,167건):

| 항목 | 값 |
|---|---|
| 이름 규칙 적중 | 1,435건 |
| KRX와 이름으로 붙은 범위 | 938 / 1,167 = 80.4% (포함매칭 + 기호 제거·대문자화) |
| 누락 | 0 / 938 = 0.00% |
| 오탐 | 상한 435/1,435 = 30.3%, 하한 206/1,435 = 14.4% |
| 판정 불가(KRX 매칭 실패) | 229건 → PENDING |

- 누락 0/938은 이름으로 붙는 범위(KRX의 80.4%) 안의 값. 「재현율 100%」로 읽지 않음
- 붙지 않은 229건이 포털에 「상장지수」 없는 이름으로 존재하는지는 측정되지 않음
- 오탐이 1% 기준을 크게 넘어 KRX 대조를 1차로 승격. 상품군 분류가 틀리면 CDI 측정 대상 집합과 비교 모집단이 왜곡됨
- 기준일 차: 포털 `setpDt`가 KRX `basDd`보다 뒤인 건은 오탐이 아니라 PENDING(상장 전). 실측 4건. 실행 시점 규칙은 [2단계 데이터 파이프라인 Flow 설계 입력](pipeline-flow.md) 「KRX 대조 실행 시점」
- DART 표지 「집합투자기구 명칭」도 같은 문자열 규칙이라 후보 선별에만 사용. 첨부 파일명 `투자설명서(etf)_….pdf`는 3건 중 1건에서만 확인되어 1차 수단으로 쓰지 않음
- ETF 판정을 정규화에서 분리한 이유: 문자열을 같게 만드는 일이 아니라 상품군을 가르는 일이며, 1차 근거가 문자열이 아니라 코드

### KRX 매칭 실패 처리 (10월 4일 PM 초안)

09-19 측정의 KRX 매칭 실패 229건을 10월 4일 공공데이터포털 전체 목록(183,724행)과 다시 대조함. 별칭 사전은 만들지 않고 아래 규칙 3개만 추가함.

| 규칙 | 내용 | 근거 |
|---|---|---|
| 괄호 표기 제거 | KRX 이름의 `(합성)`·`(H)`·`(합성 H)`를 떼고 대조. 포털은 이 표기를 이름 끝에 따로 붙임(예: KRX `ACE MSCI멕시코(합성)`, 포털 `한국투자 ACE MSCI멕시코증권상장지수투자신탁(주식-파생형)(합성)`) | 실패 원인 대부분 |
| 브랜드 개명 4건 | ACE←KINDEX, RISE←KBSTAR, PLUS←ARIRANG, KIWOOM←KOSEF. 새 브랜드로 안 붙으면 옛 브랜드로 한 번 더 대조 | 운용사 브랜드 변경 |
| 환헤지 표기로 후보 가름 | 후보가 둘 이상이면 KRX 이름에 `H)`가 있는지와 포털 이름이 `(H)`로 끝나는지를 맞춤 | 같은 이름의 환헤지·비헤지 상품 쌍 |

| 결과 | 건수 | 처리 |
|---|---|---|
| 자동 1:1 | 142 | 포털 상품에 연결, `etf_confidence = KRX_CONFIRMED` |
| 유사도 후보 | 36 | 같은 브랜드 안 이름 유사도 0.85 이상 후보 1개. 사람이 확인한 뒤 연결. 확인 전에는 PENDING |
| 수동 | 51 | 사람이 포털에서 찾아 1회 매핑. 못 찾으면 PENDING 유지(모집단 제외) |

- 결과 파일: [`krx_unmatched_rematch.csv`](../research/samples/krx_unmatched_rematch.csv), 재현: [`rematch_krx_unmatched.py`](../research/scripts/rematch_krx_unmatched.py)
- 사람이 확인·매핑한 결과(87건)는 S3 `eval/`이 아니라 대응표 파일로 저장소에 두고 수집 코드가 읽음. 담당 PM(대현), 시점은 ETF 매칭 구현 전(ETF 2순위)
- 매주 새로 상장되는 ETF도 같은 규칙을 먼저 적용하고, 붙지 않은 것만 `match_failure`에 남김
- 유사도 후보에는 틀린 연결이 섞일 수 있음(예: `KODEX 코스닥150선물인버스` ↔ 포털 `코스닥150인버스`). 그래서 자동 연결하지 않음

## 상품명 정규화

상품명(펀드명)에만 적용. 법인명은 「법인명 정규화」.

| 순서 | 단계 | 잡는 실패 사례 |
|---|---|---|
| 1 | NFKC 정규화 | "Ａ형" vs "A형", 전각 숫자·괄호 vs 반각 같은 호환 문자 차이 |
| 2 | 공백 전면 제거 | "삼성 그룹주 펀드" vs "삼성그룹주펀드" 같은 공백 개수·위치 차이 |
| 3 | (주)·주식회사 표기 제거 | 운용사 법인 표기 유무 차이("(주)미래에셋자산운용" vs "미래에셋") |
| 4 | 유형 괄호(「[주식-파생형]」 등)·호수(「제1호」, 「1호」, 「 1」)·클래스 표기(A형, C-e형, Ce, ClassA)를 각각 별도 필드로 분리 | 부가 정보를 떼어내지 않으면 유형·호수·클래스만 다른 별개 상품이 같은 상품으로 오매칭되거나, 표기 차이로 같은 상품이 다른 상품으로 오분류됨 |

- 순서가 중요한 이유: 뒤 단계가 앞 단계의 결과에 의존
- 분리한 호수 필드는 「하드 룰」에서, 클래스 필드는 매칭 이후 상품 계열 안 클래스 판정에서 사용
- 옛 「전각/반각 변환」 단계는 NFKC가 포괄하므로 따로 두지 않음
- 실측 표기 차이: DART `미래에셋밸런스롱숏증권자투자신탁1호(채권혼합)` vs 금투협 `미래에셋밸런스롱숏증권자투자신탁 1(채권혼합)`. 펀드명은 조인 키로 부적합

## 하드 룰

유사도 점수와 무관하게 탈락시키는 조건.

| 규칙 | 조건 | 근거 |
|---|---|---|
| 모자 구분 (`is_feeder`) | 「증권투자신탁」(모)과 「증권자투자신탁」(자) 구분을 별도 필드로 추출. 양쪽 값이 다르면 탈락 | 「자」 한 글자는 표기 오차가 아니라 다른 상품. 토큰 유사도는 이 차이를 사소하게 취급 |
| 호수 일치 | 분리한 호수 필드가 양쪽에서 다르면 탈락 | "OO펀드제1호"와 "OO펀드제2호"는 본체명이 거의 같지만 다른 상품 |
| ELS 회차 (Phase 1 범위 밖(9차 미팅), Phase 2 검토) | 회차 번호(「제29976회」)가 다르면 탈락 | 같은 발행사·기초자산 ELS는 회차만 다르고 이름이 거의 같음 |
| 숫자 토큰 완전 일치 | 호수를 제외한 숫자 토큰(지수명 「코스피200」 등)은 완전 일치해야 함 | 호수는 별도 필드로 처리하므로 이 규칙 범위는 호수 외 숫자로 좁힘 |

- 모자 구분 실측 사례(DART 표지 10건 안): 「신한미국나스닥100인덱스증권자투자신탁」·「카디안 월지급아시아퍼시픽고배당증권자투자신탁」·「카디안 미국뱅크론특별자산자투자신탁」은 자펀드 표기, 「신한일반채권증권투자신탁제1호」는 모펀드 표기
- ELS 식별 키 자체는 미정(「미결」). ELS는 Phase 1 범위 밖(9차 미팅), Phase 2 검토

## 유사도 방법

- 편집 거리 계열보다 토큰(부분 문자열 집합) 계열 유사도를 주 방법으로 사용
- 이유: 한국어 상품명은 짧고 숫자·영문이 섞이며 어순이 문서마다 다를 수 있음("삼성 코스피 200 인덱스" vs "삼성코스피200인덱스펀드"). 토큰 집합 기반이 어순 변화에 강함
- 토큰 유사도가 숫자 한 글자 차이를 사소하게 보는 약점은 「하드 룰」의 숫자 토큰 규칙으로 보완
- 라이브러리·알고리즘 이름은 정하지 않음

## 임계치

| 대상 | 구간 | 처리 |
|---|---|---|
| 상품명 | 0.85 이상 | 자동 매칭 |
| 상품명 | 0.60 ~ 0.85 | 매칭 후보로 남겨 사람이 확인 (라벨 대상) |
| 상품명 | 0.60 미만 | 매칭 실패 (BELOW_THRESHOLD) |
| 법인명(판매사·금융회사) | 0.95 이상 | 후보. 제재공시는 자동 확정하지 않음(「제재공시 법인 매칭」) |

적용 범위:

- 코드가 있는 소스(DART·금투협·공공데이터포털)에서 문자열 매칭은 코드 조인이 실패하거나 코드가 없는 잔여 건에만 적용
- 코드 조인 실패 잔여 건은 소량이며 사람이 볼 수 있는 규모
- 코드가 구조상 없는 소스(제재공시)는 이 표와 별개로 「제재공시 법인 매칭」 규칙 적용

한쪽 실수가 더 비쌈:

- 임계치를 낮추면 과매칭이 늘어 다른 상품의 위험등급이 잘못 붙고, CDI 정규화 모집단에 잘못된 값이 섞임. 겉으로 실패처럼 보이지 않아 발견이 늦음
- 임계치를 높이면 미매칭이 늘어 표본이 줄고 특정 상품군·판매사로 치우칠 수 있으나, 미매칭은 행 단위 로그로 보여 사후 발견·보정 가능
- 그래서 자동 매칭 기준값을 높게 잡고 애매한 구간은 사람 검증을 거침

법인명 별도 임계치:

- 판매사명은 상품명보다 짧고 반복도가 높아("OO증권", "OO은행") 상품명 임계치를 쓰면 우연히 높은 점수가 나와 과매칭 위험이 큼
- 0.90에서 0.95로 상향(09-14). 제재공시 규칙에 쓰는 값과 통일

대안 비교:

| 안 | 내용 | 판정 | 사유 |
|---|---|---|---|
| 단일 표 (현행) | 0.85 / 0.60~0.85 / 0.60 미만, 적용 범위를 코드 조인 잔여 건으로 명시 | 채택 (09-14) | 코드가 1차 수단이 되어 문자열은 잔여 처리 |
| 티켓 메모 두 벌 안 중 DART용 재현율 벌 | 코드 있는 소스 전용, 자동 확정 없이 0.80 미만만 후보에서 제외 | 채택하지 않음 (09-14) | 펀드코드 10/10으로 DART 문자열은 잔여 건 2차 수단이 되어, 기존 0.60~0.85 수동 확인 구간과 기능이 겹침 |
| 티켓 메모 두 벌 안 중 분쟁·제재 엄격 규칙 | 0.95 이상 + 단독 후보 + 교차 확인, 전건 수동 확인 | 채택 (09-14) 후 제재 한정·자동 확정 금지로 좁힘 (09-22) | 분쟁조정은 법인명 자체가 마스킹. 제재공시는 교차 확인에 쓸 칸이 판매사 마스터에 없음 |
| 판매사 임계치 0.90 | 옛 값 | 0.95로 변경 (09-14) | 짧고 반복적인 법인명의 과매칭 위험 |

- 판정 경위 원문: [09-14 초기 소스 확인](records/phase1-erd/initial-source-checks.md) 「티켓 메모 대조 판정」

## 법인명 정규화

제재공시 금융회사명(`finInstName`)에 적용. 판매회사 명단은 코드 매칭으로 바뀌어 이 규칙이 필요 없음. 제재공시는 금융회사명 문자열만 주므로 이 규칙이 유일한 수단.

| 순서 | 단계 | 잡는 실패 사례 | 근거 ([`kofia_mgmt_codes.csv`](../research/samples/kofia_mgmt_codes.csv) 원본 536건 실측) |
|---|---|---|---|
| 1 | NFKC 정규화 | 「㈜」(U+321C)가 「(주)」로 풀림. 전각 영문·숫자 해소 | 현 상호에 `㈜` 표기 사례 존재(「㈜엠에스제이투자일임」) |
| 2 | 구 상호 → 현 상호 치환 | 「아주자산운용(주)」→「글로벌원자산운용」, 「누림투자자문」→「누림자산운용」 | 536건 중 97건(18%)에 변경전 상호, 그중 44건은 업종 접미사까지 바뀜 |
| 3 | 법인격 표기 제거 (위치 무관) | 「(주) 두물머리투자자문」(전치)과 「GB투자자문(주)」(후치)를 같은 규칙으로 처리 | 현 상호 72건(13%)에 법인격 표기, 전치·후치 혼재. 제재 표본에서도 `㈜비엔케이투자증권`·`다올투자증권㈜` 혼재 |
| 4 | 공백 전면 제거 | 「퍼시픽브릿지자산운용 주식회사」 | 상호 37건에 공백 |
| 5 | 지점·본점 표기 제거 | 「OO은행 강남지점」 ↔ 「OO은행」 | 실제 표기 형태 미확인 |

- 2단계가 3단계보다 앞인 이유: 별칭 사전(`former_name`)의 구 상호에도 법인격 표기가 섞여 있음(16건, 「바로자산운용주식회사」 등). 사전 키를 같은 5단계로 미리 정규화하고 원문도 같은 순서로 처리
- 제재공시 실측: 표기가 법인격 없는 약칭(`교통은행`)이면 1~4단계는 할 일이 없고 5단계만 유효

업종 접미사는 제거하지 않음:

- 「자산운용」·「투자자문」·「증권」·「은행」 등은 법인을 가르는 식별 정보
- 제거하면 「미래에셋자산운용」과 「미래에셋증권」이 같은 문자열이 됨
- 대신 업종이 바뀐 44건은 유사도가 낮아 매칭되지 않음 → 2단계 별칭 치환이 필수. 치환 없이 접미사만 남기면 구 상호로 작성된 과거 문서가 오류 없이 매칭에 실패함

별칭 사전:

| 대상 | 사전 | 상태 |
|---|---|---|
| 운용사 | [`kofia_mgmt_codes.csv`](../research/samples/kofia_mgmt_codes.csv)의 `former_name` → `mgmt_name` 97건 + 09-22 추가 2행 | 확보 (09-14, 09-22 보강). 원본 536건 + 별칭 2행 = 538행. 표본 머리글 행 처리는 확인대기(9차 미팅): 분석·리서치(민석) |
| 판매사(증권·은행) | 없음 | 미확보(「미결」) |

- 09-22 추가 2행: 비엔케이자산운용·케이비자산운용은 다른 소스에서 `BNK자산운용`·`KB자산운용`으로도 나옴. 한글 표기만 있으면 매칭 실패하므로 별도 행 추가
- 이 파일에서 `mgmt_code` `240`·`223`은 두 번씩 나옴. `former_name → mgmt_name` 조회용으로만 사용. `mgmt_code`를 기본키로 쓰는 코드는 행을 합친 뒤 사용
- 증권사·은행의 구 상호: 제재공시는 약칭 표기라 구 상호가 나올 여지가 작음. 남는 것은 합병으로 사라진 회사의 과거 제재 건이며, 사전이 아니라 판매사 표의 유효기간으로 다룸(2단계 데이터 파이프라인 Flow 설계, SCD2)

## 제재공시 법인 매칭

- 제재공시는 상품 식별자가 없어 상품 매칭을 시도하지 않음. 본문도 `㉮펀드`로 마스킹
- `finInstName`을 「법인명 정규화」 5단계로 정규화해 distributor 후보를 찾음
- 분쟁조정은 회사명도 마스킹이므로 같은 절차로 확정할 수 없음

09-22 정정: 옛 조건 「유사도 0.95 + 단독 후보 + `actReqDate` 일치」는 구현 불가. 판매사 마스터에 `actReqDate`가 없어 비교할 날짜가 없음. 사건일은 제재 레코드·게시판 교차 확인에는 쓸 수 있으나 법인 식별의 독립 증거가 아님.

| 조건 | 처리 |
|---|---|
| 검수된 별칭·코드 대응표로 동일 법인 확인 | 근거를 기록하고 연결 |
| 문자열 단독 후보 또는 유사도 0.95 이상만 충족 | 후보로 기록. 독립 법인 근거 또는 수동 검수 전 자동 확정 금지 |
| 원문 마스킹 | 구조적 미연결. 반복 매칭 금지 |
| 명시적인 대상 업권·마스터 범위 밖임이 확인됨 | 대상 외로 기록 |
| 마스터에 없으나 범위 밖인지도 모름 | NO_CANDIDATE·검수. 미등록만으로 대상 외 단정 금지 |

「대상 외」와 「매칭 실패」 기준 (09-22). 금투협 판매회사 마스터에는 펀드를 파는 회사만 있음.

| 사유 | 뜻 | 실패율 포함 | 09-22 표본 |
|---|---|---|---|
| 업권 자체가 대상 아님 | 보험대리점·가상자산사업자처럼 구조상 펀드를 팔 수 없음 | 아님 | 3건 |
| 판매회사 미등록 | 업권은 팔 수 있는데 이 회사가 등록하지 않음 | 아님 | 1건 (토스뱅크) |
| 이름 표기 차이 | 같은 회사인데 표기가 달라 못 붙음 | 포함 | 0건 |

- 제재 표본 결과(2026-09 8건): 매칭 성공 4 / 대상 외 4 / 매칭 실패 0. 대상 외는 보험대리점 2, 가상자산사업자 1, 판매회사 미등록 1. [`fss_sanctions_match_result.csv`](../research/samples/fss_sanctions_match_result.csv)
- 토스뱅크를 대상 외로 둔 근거: 카카오뱅크가 A02079로 마스터에 있음. 인터넷은행이라 빠진 것이 아니라 이 회사가 판매회사가 아님
- 표본이 늘었을 때 은행·증권사가 미등록 사유로 반복되면 마스터가 오래된 것인지 재확인 필요
- 외국은행 국내지점(샘플 `교통은행`)·저축은행·카드·보험 등은 판매사 표에 없는 것이 정상. 미분류로 두면 실패율이 실제보다 높게 나옴
- 8건 결과를 다른 달에 일반화하지 않음
- 기록 위치: 법인 후보는 `match_failure.top1_candidate_distributor_id`, 상품 후보는 `top1_candidate_product_id`. 해결 시 `resolved_at`·`resolution_note`
- 상품 임계치 검증과 법인 임계치 검증은 다른 작업

## 매칭 실패 기록

실패는 건수가 아니라 행 단위로 남김. 실패가 ETF·특정 판매사에 몰리면 표본이 한쪽으로 치우치고, 조인에서 빠진 상품은 위험등급이 비어 분석에서 통째로 빠지기 때문.

| 칼럼 | 내용 |
|---|---|
| 원문 상품명 | 문서 표에 있던 그대로 |
| 정규화 후 문자열 | 「상품명 정규화」 4단계를 거친 결과 |
| 소스 | 어느 소스의 어느 표에서 왔는지 |
| top-1 후보 | 가장 유사도가 높았던 상품 코드·이름과 점수 (있다면) |
| 실패 사유 코드 | 아래 분류 |
| 처리 상태 | 미해결 / 수동확인중 / 보류 |

| 사유 코드 | 상태·의미 | 재처리 |
|---|---|---|
| PENDING_MASTER | 매칭 대상 상품 마스터가 아직 도착하지 않음. 정상 상태 | 30일 재시도 |
| AMBIGUOUS | 다중 후보 동점, 또는 코드 없는 소스에서 자동 확정 조건을 충족하지 못해 사람이 봐야 함 | 수동 큐 |
| NO_CANDIDATE | 후보 자체가 없음(신규상품, 상장폐지 등) | 주 1회 재시도 |
| NO_CODE_IN_SOURCE | 소스 구조상 코드·상품명을 붙일 수 없음(분쟁조정·제재공시. 상품명이 마스킹) | 재시도 대상 아님 |
| BELOW_THRESHOLD | 코드 있는 소스 잔여 건은 상품명 유사도 0.60 미만, 법인명은 0.95 미만 | 재시도 대상 아님(정규화 개선 시 재평가) |
| NORMALIZE_FAILED | 원문이 파싱 단계에서 깨져 정규화 불가 | 추출 실패와 연계([원본 보관과 수집·파싱 실패 처리 규칙](storage-and-failure-rules.md) 「추출 실패와 절 품질」) |
| CLASS_GRADE_MISMATCH | 클래스 위험등급이 펀드 대표 등급과 다름(ERD v2.2, 10월 4일 결정 대기). 불일치한 값의 출처(운용사 공시, 판매사, API)는 attempted_key_value 또는 resolution_note에 기록. 판매사 재분류 등급은 대표 등급으로 쓰지 않음([데이터 테이블·ERD 설계](data-model.md) 「상품과 법인」) | 확인 대상. 재시도 대상 아님 |

- PENDING_MASTER가 정상인 이유: DART가 금투협·공공데이터포털보다 6~18일 먼저 들어옴. DART 표지 10건 중 포털 미등록 3건이 이 상태
- NO_CODE_IN_SOURCE의 실제 원인은 「코드가 없다」가 아니라 「상품이 가려져 있다」
- 이 분류는 초안. 실제 실패 사례를 본 뒤 세분화(「미결」)
- 옛 분류(A~D)와의 대응: [ERD 설계 변천과 검토 기록](records/phase1-erd/design-review-history.md) 「대체된 옛 규칙」

## 라벨 200건 표본 요건

- 200건은 매칭 품질 검증의 목표 표본 수로만 유지
- 옛 구성 「분쟁·제재 187건 + 잔여 13건」은 쓰지 않음(09-22 정정). 187은 금융투자 분쟁조정 사건 수이며 마스킹 때문에 상품·회사 매칭 정답을 확보할 수 없음. 제재 API 확보 표본은 별도의 8건
- 상품 코드 충돌·문자열 잔여·ETF·운용사별로 검수 가능한 정답 표본을 구성하고, 제재 법인 매칭 표본과 구분
- 구체 할당은 실제 후보 분포와 CDI 산식 담당(다빈) 검수로 정함
- 임계치를 조정한 표본과 최종 평가 표본을 분리
- 제재 이력 라벨의 0건과 「관측하지 못함」은 다름. API 커버리지가 불완전한 상태에서 나머지 판매사를 무제재 음성으로 지정하지 않음
